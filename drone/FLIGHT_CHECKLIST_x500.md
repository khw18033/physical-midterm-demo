# X500 v2 비행 체크리스트 — 현장 절차서

**대상**: 현장에서 이 기체를 띄우는 사람. 라즈베리파이 쪽 구조를 몰라도 따라갈 수 있게 썼다.
**기준일**: 2026-09-22 · **기체**: X500 v2 (`x500-001`) · **컴패니언**: Raspberry Pi 5 (`pi3`)
**전제**: 야외, GPS 수신 가능한 곳. 실내에서는 `takeoff_land.py` 가 동작하지 않는다(§7 참고).

> ⚠ 이 기체는 **arm·이륙을 한 번도 해본 적이 없다.** 이 문서의 3~5단계가 첫 시도다.
> 라즈베리파이 쪽 통신 계통은 검증이 끝났고, 검증되지 않은 것은 §7에 따로 적었다.

---

## 1. 빠른 순서 (한 장)

| # | 할 일 | 통과 기준 |
|---|---|---|
| 0 | 전원 인가 (프로펠러 **제거** 상태) | 10초 내 `mode = drone` |
| 1 | 링크 확인 `check_link.py` | 종료코드 0, ATTITUDE 수신 |
| 2 | 텔레메트리 `telemetry_watch.py` | **`GPS=O home=O`** 눈으로 확인 |
| 3 | 모터 `arm_disarm_test.py` (프로펠러 **제거**) | 모터 회전 → DISARMED 복귀 |
| 4 | **프로펠러 장착 → 조종기로 수동 호버** | 안정적으로 뜨고 내린다 |
| 5 | 자동 `takeoff_land.py` | 1.5m 이륙 → 8초 → 자동 착륙 |

각 단계는 **앞 단계가 통과했을 때만** 넘어간다. 실패하면 §6 대응표로 간다.

### 장비 체크리스트

- [ ] LiPo 완충 + 여분. **첫 비행은 완충으로만**
- [ ] 프로펠러 (처음엔 **떼어 놓은 채로** 시작)
- [ ] 조종기 충전·바인딩 확인
- [ ] **FC에 SD 카드 삽입** — PX4 ulog가 여기 쌓인다. 비행이 잘못됐을 때 원인을 알려주는 유일한 기록이다
- [ ] 지상국 노트북 (QGroundControl) — Tailscale 로그인 상태
- [ ] 라즈베리파이–FC 배선: **FC TELEM2** ↔ GPIO14/15 (TX→10번, RX→8번, GND→6번)

### QGroundControl에서 미리 확인

- [ ] 센서 캘리브레이션 (가속도계·자이로·지자기) 전부 완료
- [ ] **페일세이프**: RC 상실 시 동작, 배터리 부족 시 동작
- [ ] **킬 스위치** 할당 및 동작 확인
- [ ] 비행 모드 스위치 배치 (Position / Altitude / Manual)
- [ ] FC 파라미터가 아래와 같은지 (**읽기만**, 바꾸지 말 것)

| 파라미터 | 기대값 | 의미 |
|---|---|---|
| `MAV_1_CONFIG` | 102 (TELEM 2) | 라즈베리파이 링크 |
| `MAV_1_MODE` | 2 (Onboard) | 〃 |
| `SER_TEL2_BAUD` | 921600 | 〃 |
| `MAV_0_CONFIG` / `SER_TEL1_BAUD` | 101 / 57600 | 무선 Air Unit — **건드리지 않는다** |
| `UXRCE_DDS_CFG` | 0 (Disabled) | |

## 3. 현장 절차

### 0단계 — 전원 인가

프로펠러를 **제거한 채로** 배터리를 연결한다. 라즈베리파이와 FC가 같이 켜진다.

```bash
cat ~/drone/state/mode          # drone 이어야 함 (전원 후 약 10초)
systemctl is-active drone-detect drone-mavlink-router drone-linkmon drone-node
vcgencmd get_throttled          # 0x0 이어야 함
vcgencmd measure_temp
```

- `mode = drone` 이 안 뜨면 → §6 [A]
- `get_throttled` 가 `0x0` 이 아니면 → **배터리 전원이 라즈베리파이에 부족하다.** §6 [E]
  (이 값은 드론 배터리로 켠 상태에서 처음 측정하는 것이다. 벽 전원 기준으로는 `0x0` 이었다)

### 1단계 — 링크 확인

```bash
cd ~/drone
./venv/bin/python scripts/check_link.py --device udpin:0.0.0.0:14540
```

읽기 전용이다. FC에 제어 명령을 보내지 않는다.

**통과 기준**: 종료코드 0, heartbeat 수신, ATTITUDE 수신.
참고값(2026-09-21 실측): ATTITUDE 약 100Hz, 60초당 약 19,000건, 22~23종 메시지.

### 2단계 — 텔레메트리와 GPS ★ 가장 중요

```bash
./venv/bin/python scripts/telemetry_watch.py
```

읽기 전용이다(구독만, 명령 0건). 1초에 한 줄씩 나온다.

**`GPS=O home=O` 가 뜰 때까지 기다린다.** 야외에서 보통 1~3분. 이게 안 뜨면 4·5단계는
어차피 스크립트가 스스로 거부한다.

같이 확인할 것:
- `배터리` 전압·% 가 실제와 맞는가
- `자세 r/p` 가 기체를 기울이면 따라오는가 (정지 시 변화폭 1도 미만이 정상)
- `arm=DISARMED`, `모드` 표시

확인되면 **Ctrl-C로 종료한다.** 다음 스크립트가 같은 포트(14540)를 쓰므로
**한 번에 하나만 실행한다.**

#### arm 가능 상태인지 따로 확인 — `fc_state.py`

```bash
./venv/bin/python scripts/fc_state.py
```

이건 라우터의 QGC 포트(TCP 5760)로 붙으므로 **`telemetry_watch.py` 와 동시에 돌려도 된다.**
읽기 전용(송신 0바이트)이다. 한 번 찍고 끝난다.

**arm 하려면 아래가 전부 맞아야 한다:**

| 항목 | 필요한 값 | 아니면 |
|---|---|---|
| `system_status` | **`MAV_STATE_STANDBY`** | `UNINIT` 이면 사전검사 미통과 → §6 [H] |
| `GPS` | `3D_FIX` 이상, 위성 다수 | `NO_GPS`(0)는 모듈 미검출, `NO_FIX`(1)는 하늘 가림 → §6 [I] |
| 센서 헬스 `RC` | **`O`** | `X` 면 조종기가 꺼져 있거나 미바인딩 |
| 센서 헬스 나머지 | 전부 `O` | |

### 3단계 — 모터 계통 (프로펠러 제거 상태)

> ⚠ **프로펠러가 제거돼 있는지 다시 확인한다.** 기체를 단단히 잡거나 고정하고,
> 주변에 사람이 없게 한다.

```bash
./venv/bin/python scripts/arm_disarm_test.py
```

`"프로펠러를 제거했습니까?"` 에 `yes` 를 입력해야 진행된다. arm → 3초 → disarm.

**통과 기준**: 모터 4개가 전부 돌고, 끝나고 `DISARMED ✔`.
- arm이 거부되면 → §6 [C] (FC의 arm 전 검사에 걸린 것이다. 대개 정상적인 거부다)
- ⚠ disarm이 실패하면 **즉시 배터리를 분리한다**

### 4단계 — 조종기로 수동 호버 ★ 자동 이륙보다 먼저

프로펠러를 장착한다. 사람·장애물에서 충분히 떨어진다.

**조종기로 직접 띄워서 낮게 호버하고 착륙시킨다.** 스크립트를 쓰지 않는다.

기체 자체가 제대로 뜨는지를 먼저 확인하는 단계다. 이걸 건너뛰고 5단계로 가면,
문제가 생겼을 때 **기체 탓인지 라즈베리파이 경로 탓인지 분리할 수 없다.**

**통과 기준**: 안정적으로 뜨고, 떠 있고, 내려온다. 이상 진동·기울어짐·드리프트 없음.

### 5단계 — 자동 이륙·착륙

> ⚠ **조종기를 손에 들고, 언제든 개입할 수 있는 상태에서 실행한다.**

```bash
./venv/bin/python scripts/takeoff_land.py
```

확인 문구에 `yes` 입력 → 위치 추정 확인 → arm → 1.5m 이륙 → 8초 호버 → 자동 착륙.

스크립트가 스스로 막는 것:
- 이미 ARM 상태면 중단
- 위치 추정(`is_global_position_ok` + `is_home_position_ok`)이 정상이 아니면 **이륙하지 않음**
- 이륙 고도 설정 실패 시 **arm 하지 않고 중단**
- takeoff 실패 시 disarm 시도
- 중간에 무슨 일이 있어도 `finally` 로 land 호출

**land 가 실패하면 스크립트가 할 수 있는 일이 없다. 즉시 조종기로 개입한다.**

## 4. 중단 기준 — 이럴 땐 접는다

하나라도 해당하면 그날은 비행하지 않는다.

- `GPS=O home=O` 가 5분 넘게 안 뜬다
- `get_throttled` 가 `0x0` 이 아니다 (전원 부족 — 공중에서 라즈베리파이가 죽을 수 있다)
- 3단계에서 모터 회전이 고르지 않거나 소리가 이상하다
- 4단계 수동 호버가 불안정하다
- 조종기 킬 스위치 동작이 확실하지 않다
- 바람이 세거나 주변에 사람이 있다
- 배터리가 완충이 아니다

## 4-1. 비행 중 이상 상황 — 무슨 일이 일어나는가

### 나가기 전에 반드시 한 번 돌릴 것

```bash
./venv/bin/python scripts/failsafe_audit.py
```

읽기 전용이다(파라미터를 읽기만 하고 쓰지 않는다). TCP 5760 을 쓰므로 다른 도구와 겹치지 않는다.
**이 기체의 실제 설정으로** 아래 세 가지에 답해 준다. 값을 모르고 띄우지 말 것.

### ▸ 라즈베리파이가 죽으면 (전원 차단·브라운아웃·SSH 끊김)

**기체는 떨어지지 않는다.** 비행 제어는 FC 가 전담하고, 라즈베리파이는 명령을 **'시작'만**
시킨다. `takeoff_land.py` 가 보내는 `takeoff()` / `land()` 는 PX4 의 **모드 전환 명령**이지
연속 제어가 아니다. 한 번 보내면 FC 가 알아서 끝까지 수행한다.

> OFFBOARD 모드라면 스트림이 끊기는 즉시 페일세이프가 걸린다. **우리는 OFFBOARD 를 쓰지 않는다**
> (`UXRCE_DDS_CFG=0`, offboard 스크립트 없음). 그래서 라즈베리파이가 죽어도 즉각적인 영향이 없다.

**대신 이게 위험하다:** 이륙 직후 라즈베리파이가 죽으면 **`land()` 명령이 영영 오지 않는다.**
기체는 그 고도에서 계속 호버한다. → **조종기로 직접 내려야 한다.**
5단계에서 "조종기를 손에 들고"라고 한 이유가 이것이다.

`NAV_DLL_ACT` 가 0 이 아니면 FC 가 스스로 RTL·착륙할 수도 있다. `failsafe_audit.py` 로 확인한다.

### ▸ 라즈베리파이는 살아 있는데 링크만 끊기면

자동으로 복구된다. 그 동안에도 **기체는 정상 비행한다.**

| 고장 | 복구 시간 |
|---|---|
| 시리얼 포트 점유 | 약 35초 |
| 프로세스 hang | `drone-node` 45초 / `drone-detect` 52초 |
| 프로세스 급사 | 약 6초 |

`logs/linkmon.log` 와 journal 에 끊김·복구가 기록된다.

### ▸ 배터리

**두 가지를 구분해야 한다.**

1. **FC 의 배터리 페일세이프** — `COM_LOW_BAT_ACT` 에 따라 RTL·착륙한다. 기체를 지키는 장치다
2. **라즈베리파이의 전원 부족** — 라즈베리파이가 드론 BEC 에서 먹는다면, 비행 중 스로틀이
   확 올라갈 때 전압이 내려가 **라즈베리파이만 먼저 꺼질 수 있다.** 그러면 위의
   "라즈베리파이가 죽으면" 항목이 된다. 0단계의 `vcgencmd get_throttled` 가 이걸 미리 잡는 검사다

### ▸ ⚠ SD 카드 손상

비행 중 라즈베리파이의 전원이 갑자기 끊기면 **SD 카드 파일시스템이 깨질 수 있다.**
`drone-agent` 가 스풀에 계속 쓰고 있으면 위험이 커진다.

완화:
```bash
sudo systemctl stop drone-agent    # 첫 비행 동안 카메라 노드 정지
sync                               # 비행 직전 디스크 flush
```
비행 후 `sudo systemctl start drone-agent` 로 되돌린다.

## 5. 지상국 (선택)

QGroundControl을 붙여 두면 상태를 한눈에 본다. 비행 필수는 아니다.

- 연결: **TCP `100.85.243.54:5760`** (라즈베리파이 Tailscale IP)
- 지상국 장비: `desktop-oaujese` (`100.125.71.51`)
- 안 붙으면: 노트북에서 `tailscale ping pi3`

가시화 웹은 `ws://pi3.local:9001` (MQTT over WebSocket). **읽기 전용이라 웹에서는 못 띄운다.**

## 6. 증상별 대응

### [A] `mode` 가 `none` 에서 안 바뀐다

```bash
journalctl -u drone-detect -n 40 --no-pager
ls -l /dev/ttyAMA0
```
- FC 전원이 들어왔는지, TELEM2 커넥터가 꽂혔는지 확인 (가장 흔한 원인)
- 감지는 10초 간격으로 계속 재시도한다. **FC 전원이 늦게 들어와도 알아서 붙는다**
- 배선이 맞는데도 안 되면 TX/RX가 바뀌었을 수 있다 (FC TX→10번, FC RX→8번)

### [B] `check_link.py` 는 되는데 `telemetry_watch.py` 가 연결 안 됨

14540 포트를 다른 스크립트가 쓰고 있다. **한 번에 하나만 실행한다.**
```bash
ss -ulnp | grep 14540
```

### [C] arm이 거부된다

FC의 arm 전 검사(preflight check)에 걸린 것이고, **대개 정상적인 거부다.**
QGroundControl을 붙이면 거부 사유가 글로 나온다. 흔한 원인: GPS 부족, 지자기 캘리브레이션 필요,
RC 미연결, 기체가 수평이 아님.

### [D] 비행 중 라즈베리파이 링크가 끊겼다

**기체는 계속 난다.** 라즈베리파이는 읽기 위주이고 비행 제어는 FC와 조종기가 한다.
조종기로 착륙시키면 된다. 링크는 스스로 복구된다(자동 복구 시간: 포트 점유 35초,
프로세스 hang 45~52초, 급사 6초).

### [E] `get_throttled` 가 `0x0` 이 아니다

드론 배터리에서 라즈베리파이로 가는 전원이 부족하다. **비행하지 않는다.**
BEC 용량, 배선 굵기, 커넥터 접촉을 점검한다. 공중에서 컴패니언이 죽으면 기록이 끊긴다.

### [F] 시리얼을 수동으로 직접 써야 할 때

`drone-detect` 가 포트를 두고 다투지 않게 정비 모드를 켠다.
```bash
touch ~/drone/state/maintenance    # 켜기
rm    ~/drone/state/maintenance    # 끄기 (끝나면 반드시)
```
※ 1~5단계는 전부 라우터 경유(14540)라 **정비 모드가 필요 없다.**

### [H] `Preflight Fail: heading estimate not stable` / `system_status = UNINIT`

PX4 의 EKF 가 **기수 방향(heading)을 확정하지 못한 상태**다. 이 상태로는 arm 이 거부되고
`system_status` 도 `STANDBY` 로 올라가지 않는다. **통신 문제가 아니다** — 링크는 멀쩡하다.

흔한 원인, 흔한 순서대로:
1. **실내다.** 건물 철골·전원장치의 자기 간섭으로 지자기가 흔들린다. **야외로 나가면 대개 풀린다**
2. GPS 가 없어 GPS 보조 기수 추정이 안 된다 ([I] 를 먼저 해결)
3. 지자기(컴퍼스) 캘리브레이션이 필요하다 → QGC 에서 수행
4. 기체를 방금 움직였다 → 수평인 곳에 가만히 두고 1~2분 기다린다

확인: `./venv/bin/python scripts/fc_state.py` 를 야외에서 다시 돌려 `STANDBY` 가 되는지 본다.

**GPS 와 heading 은 대개 한 뿌리다.** 실측된 FC 설정은 `EKF2_GPS_CTRL=7`(EKF 가 GPS 를 쓰도록
설정됨), `EKF2_MAG_TYPE=0`(자동), `COM_ARM_MAG_ANG=60`. GPS 데이터가 하나도 없으면 EKF 는
GPS 보조 기수 추정을 잃고 지자기에만 의존하는데, 실내에서는 그것만으로 수렴하지 못한다.
→ **[I] 의 GPS 를 먼저 해결하면 heading 도 같이 풀릴 가능성이 높다.**

참고로 `COM_ARM_WO_GPS=1` 이라 **GPS 자체가 arm 을 막는 조건은 아니다.** 막는 건 heading 이다.

### [I] GPS 가 안 잡힌다 — `NO_GPS` 와 `NO_FIX` 를 구분할 것

> 2026-09-22 실측: `SYS_HAS_GPS=1` (기체가 GPS 가 있다고 선언) 인데 `fix_type=0`·위성 0개였다.
> **PX4 는 GPS 를 기대하는데 데이터가 아예 안 온다**는 뜻이라 배선 쪽이 유력하다.

`fc_state.py` 의 `fix_type` 숫자가 원인을 가른다.

| 표시 | 뜻 | 조치 |
|---|---|---|
| `NO_GPS` (0), 위성 **0개** | FC 가 **GPS 장치 자체를 못 본다** | 기다려도 소용없다. GPS 모듈 커넥터(FC 의 GPS1 포트)와 마스트 배선을 확인한다 |
| `NO_FIX` (1) / `2D_FIX` (2) | 장치는 있는데 위성이 부족하다 | 하늘이 트인 곳에서 1~3분 더 기다린다 |
| `3D_FIX` (3) 이상 | 정상 | 진행 |

| 항목 | 어느 단계에서 밝혀지나 |

  옵티컬 플로우·외부 측위를 붙이고 코드를 고쳐야 한다
