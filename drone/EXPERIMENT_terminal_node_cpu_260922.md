# 실험 보고 — 말단 노드를 포함한 CPU 사용량 측정

- **일시** 2026-09-22 12:09 ~ 12:14 (KST)
- **장비** Raspberry Pi 5 Model B Rev 1.1 (`pi3`), 4코어 @ 2.4GHz, X500 v2 컴패니언 컴퓨터
- **측정자** 자동 측정 스크립트 `~/drone/bench/run_bench_agent.sh`

---

## 1. 목적

X500 v2 드론의 컴패니언 컴퓨터(Pi 5)에서 **드론 연결 프로그램**과 **말단 노드**를
같이 돌렸을 때 CPU 여유가 얼마나 남는지 실측한다.

답해야 할 것은 셋이다.

1. 드론 프로그램만 켜져 있을 때
2. 말단 노드만 켜져 있을 때
3. 둘 다 켜져 있을 때 ← **실제 운용 상태**

---

## 2. 측정 대상

### 2-1. 드론 프로그램 (`~/drone`)

FC(코아 H743, PX4)와 MAVLink 로 연결해 상태를 MQTT 로 내보내는 묶음이다.

| 유닛 | 하는 일 |
|---|---|
| `drone-mavlink-router` | `/dev/ttyAMA0` @921600 파싱 → UDP 4곳 + TCP 5760 팬아웃 |
| `drone-node` | udp/14543 수신 → MQTT 발행 (가시화 브리지) |
| `drone-linkmon` | udp/14541 링크 감시·통계 |
| `drone-detect` | udp/14542 링크 끊김 감시, `drone.target` 관리 |
| `mosquitto` | MQTT 브로커 (이 파이가 직접 브로커다) |

### 2-2. 말단 노드 (`~/drone_rpi`, `drone-agent.service`)

카메라로 찍어 정렬하고 엣지에 넘기는 인지 파이프라인의 말단이다.
**검출·추적·거리 산출은 엣지 몫이고 여기엔 없다.**

| 단계 | 내용 |
|---|---|
| 캡처 | `rpicam-vid` MJPEG, imx708, **1280×720 @ 8fps**, JPEG 품질 85 |
| 정렬 | KLT 광류로 프레임 간 전역 움직임 추정 — 실측 **6~7ms/프레임**, 작업 해상도 640 |
| 서버 | `0.0.0.0:8890` — 엣지가 **당겨 간다**(pull). 말단은 먼저 연결하지 않는다 |
| 스풀 | 링크 단절 구간을 디스크에 남긴다 (최대 500건 / 1800초) |

## 3. 방법

### 3-1. 시나리오

서비스를 껐다 켜며 4가지를 연속 측정했다. 기준선을 넣은 이유는 OS 상시 부하를
빼야 각각의 **순수 증분**이 나오기 때문이다.

| # | 시나리오 | 드론 | 말단 |
|---|---|:--:|:--:|
| 0 | 기준선 | ✗ | ✗ |
| 2 | 말단 노드만 | ✗ | ✓ |
| 1 | 드론만 | ✓ | ✗ |
| 3 | 둘 다 (실제 운용) | ✓ | ✓ |

순서를 `0 → 2 → 1 → 3` 으로 짠 것은 드론 스택을 두 번만 껐다 켜면 되기 때문이다.
드론 기동 후에는 `state/mode` 가 `drone` 이 되고 라우터·linkmon 이 active 가 될
때까지 기다린 뒤 측정을 시작했다 — 링크가 붙기 전을 재면 의미가 없다.

시나리오당 **워밍업 10초 + 본측정 60초**.

### 3-2. 측정 도구

`~/drone/bench/cpuwatch.py` — `/proc/<pid>/stat` 을 1초 간격으로 표집해
구간 델타를 낸다. 프로세스를 네 그룹으로 나눈다.

| 그룹 | 대상 |
|---|---|
| `drone` | 위 2-1 의 5개 |
| `agent` | `agent.py`, `rpicam-vid` |
| `noise` | VS Code Remote + Claude Code (개발 환경) |
| `other` | 커널 스레드, `tailscaled`, systemd 등 |

### 3-3. 개발 환경을 결과에서 뺀 이유

측정 당시 이 파이에는 VS Code Remote Server 와 Claude Code 가 붙어 있었고
**이것만 2.75~4.53 core%** 를 썼다. 비행 중에는 없는 부하이므로 `noise` 그룹으로
분리해 결과에서 제외했다.

### 3-4. 단위

- `core%` — 코어 1개를 100% 로 본 값. `top` 의 `%CPU` 와 같은 눈금
- `sys%` — 4코어 전체를 100% 로 본 값 = `core% / 4`

## 4. 결과

### 4-1. 시나리오별

| 시나리오 | 드론 | 말단 | OS/기타 | **시스템 실부하** | sys% | 온도 |
|---|---:|---:|---:|---:|---:|---:|
| 0. 기준선 | 0.00 | 0.00 | 0.40 | **0.21** | 0.05 | 59.3°C |
| 2. 말단만 | 0.00 | 30.87 | 4.47 | **36.24** | 9.06 | 62.0°C |
| 1. 드론만 | 13.18 | 0.00 | 7.11 | **20.32** | 5.08 | 60.4°C |
| 3. 둘 다 | 15.93 | 31.22 | 8.10 | **54.99** | **13.75** | 64.2°C |

> 단위는 전부 `core%`. "시스템 실부하" = 시스템 전체 busy − 개발 환경 − 측정기.
> 모든 시나리오에서 `throttled=0x0` — 스로틀 없음, 클럭 2.4GHz 유지.

**답:**

1. 드론 프로그램만 → **13.18 core% (4코어 중 3.30%)**
2. 말단 노드만 → **30.87 core% (4코어 중 7.72%)**
3. 둘 다 → **54.99 core% (4코어 중 13.75%)**

### 4-2. 가산성 — 경쟁 손실이 없다

```
따로 잰 합  36.24 + 20.32 − 0.21(기준선 중복) = 56.35
같이 잰 값                                      54.99   (−2%)
```

같이 돌려도 **손해 보는 구간이 없다.** 4코어에 부하가 고르게 퍼져 서로 코어를
다투지 않는다.

### 4-3. 프로세스 내역 (시나리오 3)

| 그룹 | 프로세스 | core% | 비중 |
|---|---|---:|---:|
| 말단 | `agent.py` (KLT + JPEG + 서버 + 스풀) | **26.57** | 85% |
| 말단 | `rpicam-vid` (MJPEG 캡처) | 4.65 | 15% |
| | **말단 소계** | **31.22** | |
| 드론 | `drone-node` | 4.55 | 29% |
| 드론 | `drone-linkmon` | 4.13 | 26% |
| 드론 | `drone-detect` | 3.97 | 25% |
| 드론 | `mavlink-routerd` | 3.23 | 20% |
| 드론 | `mosquitto` | 0.03 | 0% |
| | **드론 소계** | **15.93** | |

두 가지가 눈에 띈다.

- **말단 부하의 85% 가 `agent.py`** 다. 캡처(`rpicam-vid`)는 4.65 뿐이다.
  비용은 찍는 데가 아니라 **찍은 뒤 처리**에 있다
- 드론 쪽에서 `mavlink-routerd` 가 **가장 적게** 쓴다. C 로 짜인 라우터는
  파싱·포워딩이 싸고, 비싼 쪽은 **같은 스트림을 각자 다시 파싱하는 파이썬
  소비자 3개**(12.65 = 드론 소계의 79%)다

### 4-4. 프레임 드롭 없음

| 측정창 | 프레임 | 실효 fps |
|---|---:|---:|
| 시나리오 2 (12:10:50~12:11:50) | 480 | **8.00** |
| 시나리오 3 (12:13:30~12:14:30) | 480 | **8.00** |

드론 스택을 같이 돌려도 목표 8fps 가 그대로 유지됐다.

### 4-5. iowait — CPU 가 아닌 부담

| 시나리오 | iowait (core%) |
|---|---:|
| 0. 기준선 | 0.32 |
| 1. 드론만 | 0.70 |
| 2. 말단만 | **12.03** |
| 3. 둘 다 | **11.81** |

말단 노드가 돌면 iowait 가 **12 core%** 로 뛴다. **디스크 스풀(JPEG 쓰기)** 때문이다.
CPU 를 태우는 것은 아니지만 **SD 카드에 지속적인 쓰기 압력**이 걸린다는 뜻이고,
장시간 비행에서는 카드 수명과 쓰기 지연을 따로 봐야 한다.

참고로 `spool_after_idle_s=5.0`, `spool_min_interval_s=1.0` 설정상 **엣지가 붙어
있으면 스풀하지 않는다.** 위 iowait 는 엣지가 끊긴 구간이 섞인 값이다(4-6 참고).

### 4-6. 엣지 연결 상태가 시나리오마다 달랐다 — 결론에는 영향 없음

| 시나리오 | 엣지 | 말단이 하는 일 | 말단 CPU |
|---|---|---|---:|
| 2. 말단만 | **연결** (프레임을 당겨 감) | 캡처 + KLT + **HTTP 전송** | 30.87 |
| 3. 둘 다 | **단절** (스풀로 전환) | 캡처 + KLT + **디스크 쓰기** | 31.22 |

의도한 조건이 아니라 서비스를 껐다 켜면서 엣지 연결이 끊긴 결과다. 그런데
**차이가 0.35 core%(1%)뿐이다.** 엣지가 당겨 가든 스풀하든 어차피 JPEG 를
만들기 때문이다. 결론을 바꾸지 않는다.

## 5. 측정 조건 — 읽을 때 같이 봐야 할 것

| 항목 | 값 |
|---|---|
| FC 링크 | 연결 (`state/mode = drone`) |
| MAVLink 부하 | **20,609 msg/60초 / 26종**, ATTITUDE 100Hz, HIGHRES_IMU 50Hz |
| **QGroundControl** | **접속됨** — `desktop-oaujese`(100.125.71.51) → Tailscale → TCP 5760 |
| 카메라 | imx708 (Camera Module 3), 1280×720 @ 8fps |
| 엣지 | 시나리오 2 접속 / 시나리오 3 단절 |
| 클럭·스로틀 | 2.4GHz 유지, `throttled=0x0` (전 구간) |

### ⚠ QGC 접속이 드론 수치를 끌어올린다

같은 날 오전(10:28, QGC 미접속)에 잰 드론 값은 **6.92 core%** 였다.
지금은 **13.17** — 1.9배다. `logs/linkmon.log` 에 전환 시각이 그대로 남아 있다.

```
11:52:58   19,018건 / 21종     ← QGC 미접속
11:53:58   19,628건 / 32종     ← 이 순간 접속 (파라미터 다운로드 버스트)
11:54:58   21,074건 / 27종     ← 이후 계속
```

QGC 가 붙으면서 늘어난 일:

1. 라우터가 TCP 엔드포인트로 전량 팬아웃한다 (소켓 송신 큐에 47KB 적체 —
   Tailscale 링크가 데이터 속도를 못 따라간다)
2. FC 가 스트림 종류를 6개 더 내보낸다 (21종 → 27종, 건수 +8%)
3. 라우터가 그것을 14541·14542·14543 으로도 라우팅하므로 파이썬 소비자 3개가
   더 많은 종류를 파싱한다
4. `tailscaled` 가 그 트래픽을 터널로 나른다 — **5.21 core%** (OS/기타 급증의 주범)

**정직하게 — 완전히는 설명되지 않는다.** 트래픽 증가는 +8% 인데 소비자 CPU 는
+90% 다. 팬아웃 경로 추가와 전체 부하 상승에 따른 경쟁이 나머지를 설명하는
것으로 보이지만, QGC 를 끊고 재측정해야 정확히 나눌 수 있다. QGC 는 지상국 PC
쪽이라 이 실험에서는 끊을 수 없었다.

**어느 값을 쓸 것인가**: 비행 중에는 지상국이 붙어 있는 것이 정상이므로
**이 표(QGC 접속)가 운용 기준**이고, 오전의 6.92 는 QGC 없는 하한선이다.

## 6. 결론

- **둘 다 켜고 운용해도 Pi 5 4코어 중 약 14% 만 쓴다.** 스로틀 없음, 온도 64°C.
  **여유가 충분하다**
- 두 부하는 **거의 완전히 가산적**이다. 같이 돌려서 잃는 것이 없고,
  카메라 프레임도 8.00fps 로 떨어지지 않는다
- 부하의 중심은 **말단 노드(31.22) 이고, 그중 85% 가 `agent.py` 의 캡처 후
  처리**다. 드론 스택(15.93)은 그 절반이다
- 줄일 여지가 보이는 곳은 두 군데다. **다만 지금 수치로는 최적화할 이유가 없다**
  - 드론: `drone-detect` 와 `drone-linkmon` 이 둘 다 링크 생사만 본다 —
    합치면 약 4 core% 절감
  - 말단: 세 소비자가 같은 MAVLink 스트림을 중복 파싱하는 구조와 같은 문제
- **CPU 보다 먼저 볼 것은 iowait 12 core%** 다. 스풀 디스크 쓰기가 SD 카드에
  지속 압력을 준다 — 장시간 비행에서 따로 확인할 것

## 7. 재현

```bash
cd ~/drone/bench
sudo -v                                    # 0·2번은 드론 스택 정지가 필요하다
SECS=60 WARMUP=10 ./run_bench_agent.sh     # 4개 시나리오, 약 6분
cat results/agent_run.log                  # 진행 로그
ls results/agent/*.json                    # 원본 (프로세스별 jiffies 포함)
```

`run_bench_agent.sh` 는 trap 으로 **반드시 전부 복구**한다(드론 스택 + `drone-agent`).
중간에 끊어도 서비스가 내려간 채로 남지 않는다.

측정 후 상태: `mode=drone`, 7개 유닛 전부 active, `systemctl --failed` 0건.

| 파일 | 용도 |
|---|---|
| `bench/cpuwatch.py` | `/proc` 기반 CPU 샘플러 (그룹 분류 포함) |
| `bench/run_bench_agent.sh` | 이 실험의 4개 시나리오 드라이버 |
| `bench/results/agent/*.json` | 측정 원본 |
| `bench/results/agent_run.log` | 실행 로그 (위 타임라인의 출처) |
