### 원인: QGroundControl 이 붙었다

`logs/linkmon.log` 에 전환 시각이 그대로 찍혀 있다.

```
11:52:58   19,018건 / 21종     ← QGC 미접속
11:53:58   19,628건 / 32종     ← 이 순간 붙었다 (파라미터 다운로드 버스트)
11:54:58   21,074건 / 27종     ← 이후 계속
```

- 오전(QGC 미접속) 평균 **19,017건 / 21종**
- 지금(QGC 접속) 평균 **20,609건 / 26종** — **+8% 건수, +24% 종류**

현재 연결: `100.125.71.51:59663 → 5760` = `desktop-oaujese`
(= `drone.env` 의 `GCS_TS_NAME`). 오전 10:22 확인 때는 `5760` 에 `LISTEN` 만
있었고 `ESTAB` 이 없었다.

QGC 가 붙으면서 늘어난 일:

1. `mavlink-routerd` 가 TCP 엔드포인트로 **전량 팬아웃**한다.
   소켓 송신 큐에 47KB 가 밀려 있다 — Tailscale 링크가 데이터 속도를 못 따라간다
2. FC 가 QGC 요청으로 **스트림 종류를 6개 더** 내보낸다
3. 라우터가 그것을 14541·14542·14543 으로도 라우팅하므로 파이썬 소비자 3개가
   **더 많은 종류를 파싱**한다
4. `tailscaled` 가 그 트래픽을 터널로 나른다 — **5.21 core%** (OS/기타 급증의 주범)

### 정직하게 — 완전히는 설명되지 않는다

트래픽 증가는 +8% 인데 파이썬 소비자 CPU 는 +90% 다. 팬아웃 경로 추가와
시스템 전체 부하 상승에 따른 경쟁이 나머지를 설명하는 것으로 보이지만,
**QGC 를 끊고 재측정하지 않는 한 정확히 나눌 수 없다.** QGC 는 지상국 PC 쪽이라
여기서 끊을 수 없었다.

QGC 를 끊어 주시면 2분 안에 정확히 분리해 낼 수 있다.

### 그래서 어느 쪽을 써야 하나

**이 표(QGC 접속)가 실제 운용 기준이다.** 비행 중에는 지상국이 붙어 있는 것이
정상이므로, 오전의 6.92 는 QGC 없는 하한선이다.

### 어제 측정과 달라진 점

**말단 노드가 카메라를 배타 점유한다.** 그래서 어제 쓰던 `cam_capture.py`(15fps)를
동시에 돌릴 수 없고, 돌릴 이유도 없다 — 실제 카메라 소비자는 말단 노드다.
카메라 축을 `cam_capture.py` → 말단 노드로 바꿨다.

참고로 성격이 다르다:

| | 어제 `cam_capture.py` | 오늘 말단 노드 |
|---|---|---|
| 프레임 | 15fps, RGB888 원본 배열 | 8fps, MJPEG |
| 하는 일 | 받아서 버림 | KLT 정렬 + JPEG + HTTP 서버 + 스풀 |
| CPU | 3.78 core% | **30.87 core%** |

프레임이 절반인데 CPU 는 8배다 — 차이는 전부 **캡처 이후의 처리**다.

## 도구

`bench/cpuwatch.py` 에 `agent` 그룹을 추가했다(`drone_rpi|agent\.py|rpicam-vid`).
`camera` 그룹보다 **먼저** 와야 한다 — `rpicam-vid` 는 에이전트의 자식이다.

```bash
cd ~/drone/bench
sudo -v
SECS=60 WARMUP=10 ./run_bench_agent.sh    # 4개 시나리오, 약 6분
cat results/agent_run.log
```

`run_bench_agent.sh` 는 드론 스택과 `drone-agent` 를 껐다 켜며 측정하고,
trap 으로 반드시 전부 복구한다. 드론 기동 후에는 `mode=drone` 과 라우터가
active 가 될 때까지 기다린 뒤 측정을 시작한다.

**측정 후 상태**: `mode=drone`, 7개 유닛 전부 active, `systemctl --failed` 0건.
