# CPU 사용량 측정 보고 — 드론 프로그램 / 카메라

- 1차 측정 2026-09-21 (FC 미연결)
- **2차 측정 2026-09-22 10:28~10:33 (FC 연결) ← 이 값이 실제 운용 기준**

## 결론 (FC 연결, 카메라 1280×720 @15fps)

| # | 시나리오 | core% (코어1개 기준) | sys% (4코어 전체) |
|---|---|---:|---:|
| 1 | **드론 프로그램만** | **6.93** | **1.73** |
| 2 | **카메라만 (15fps)** | **3.78** | **0.95** |
| 3 | **둘 다** | **11.75** | **2.94** |

Pi 5 4코어 중 **약 2.9%**. 스로틀 없음(`0x0`), 온도 54→59°C.
**여유가 충분하다** — 카메라를 붙여도 코어 1개의 12%도 안 쓴다.

> 위 값은 프로세스에 정확히 귀속된 CPU다. 여기에 **시리얼 IRQ 약 0.7 core%**
> (921600 baud UART 인터럽트)가 더 붙는다. 커널 인터럽트 컨텍스트라 프로세스에
> 안 잡히는 비용이다. 기준선의 irq+softirq는 0.03이었다.

### 예상과 달랐던 것

측정 전에는 `mavlink-routerd`가 주 부하일 거라고 봤는데, **실제로는 가장 적게 쓴다(1.33).**
C로 짜인 라우터는 파싱·포워딩이 싸고, **비싼 쪽은 같은 스트림을 각자 다시 파싱하는
파이썬 소비자 3개**(2.03 + 1.83 + 1.70 = **5.56, 전체의 80%**)다.

셋이 같은 MAVLink 스트림(19,017건/60초)을 pymavlink로 중복 파싱하고 있다.
줄이고 싶다면 여기가 대상이다.

- `drone-detect`와 `drone-linkmon`은 하는 일이 겹친다 — 둘 다 링크 생사만 본다.
  합치면 **약 1.7 core%** 를 바로 줄일 수 있다
- 세 소비자가 필요한 메시지 종류를 `mavlink-router`에서 필터링해 받으면
  파싱량 자체가 준다 (지금은 ATTITUDE 100Hz까지 전부 받는다)

**다만 지금 수치로는 최적화할 이유가 없다.** 4코어 중 2.9%다.

## 측정 조건

| 항목 | 값 |
|---|---|
| 보드 | Raspberry Pi 5 Model B Rev 1.1, 4코어 @ 2.4GHz |
| 카메라 | **imx708** (Raspberry Pi Camera Module 3) |
| 캡처 | 1280×720 RGB888 **@ 15.00 fps** (실측 15.00, 41MB/s) — 백엔드 `picamera2` 0.3.37 |
| FC 링크 | **연결** (`state/mode = drone`), 라우터·linkmon active |
| MAVLink 부하 | **19,017건/60초 = 317 msg/s**, ATTITUDE 100Hz, HIGHRES_IMU 50Hz, 21종 |
| 측정 | 시나리오당 워밍업 10초 + 본측정 60초, `/proc` 1초 샘플링 |

### 단위

- `core%` — 코어 1개를 100%로 본 값 (`top`의 `%CPU`와 같은 눈금)
- `sys%` — 4코어 전체를 100%로 본 값 = `core% / 4`

### 잡음 분리

VS Code Remote + Claude Code가 3~4 core%를 쓴다. 측정기가 프로세스를 그룹으로
나눠 이 묶음(`noise`)을 결과에서 제외했다.

### 가산성 — 약간의 경쟁이 있다

6.93 + 3.78 = 10.71 인데 실측은 11.75 (**+10%**).
같이 돌리면 드론이 6.93 → 7.78 (+12%), 카메라가 3.78 → 3.97 (+5%)로 오른다.
메모리 대역폭·스케줄링 경쟁이다. 작지만 무시하고 단순 합산하면 과소평가된다.

**카메라 프레임 드롭은 없다** — 두 시나리오 모두 정확히 15.00 fps (1039프레임/69.7초).

## 부수적으로 처리한 것 (2026-09-21)

### 1. 저널이 재부팅 때 날아가던 문제

Raspberry Pi OS가 SD카드 보호용으로 `/usr/lib/systemd/journald.conf.d/40-rpi-volatile-storage.conf`
에 `Storage=volatile`을 박아 둔다. 그래서 9/21 FC 연결 세션의 저널이 통째로 사라졌다.

덮어쓰는 드롭인을 만들었다 (`/etc/`가 `/usr/lib/`보다 우선):

```ini
# /etc/systemd/journald.conf.d/50-persistent.conf
[Journal]
Storage=persistent
SystemMaxUse=200M
```

`journalctl --flush` 까지 해서 지금은 `/var/log/journal/`에 쌓인다.
`SystemMaxUse=200M`으로 SD카드 쓰기에 상한을 걸었다.

### 2. `python3-picamera2` 설치

`sudo apt install -y --no-install-recommends python3-picamera2` (0.3.37).
시스템 python3(3.13)에 들어간다 — `~/drone/venv`는 `include-system-site-packages=false`
라 venv에서는 안 보인다. 카메라 코드는 시스템 `python3`로 실행한다.

## 만든 파일

| 파일 | 용도 |
|---|---|
| [`bench/cpuwatch.py`](bench/cpuwatch.py) | `/proc` 기반 CPU 샘플러. 프로세스를 drone/camera/noise/other 그룹으로 나눠 구간 평균을 낸다 |
| [`bench/cam_capture.py`](bench/cam_capture.py) | 카메라 15fps 프레임 추출기. `picamera2` 우선, 없으면 `rpicam-vid` MJPEG 폴백 |
| [`bench/run_bench.sh`](bench/run_bench.sh) | 4개 시나리오 연속 측정. 드론 정지/복구를 trap으로 보장하고, **FC 링크가 실제로 올라온 뒤**(`mode=drone` + 라우터·linkmon active) 측정을 시작한다 |
| [`bench/run_fc.sh`](bench/run_fc.sh) | sudo 없이 시나리오 1·3만 측정 (드론 정지가 필요 없는 조합) |
| `bench/results/` | 측정 원본 JSON + 로그 |

### 다시 돌릴 때

```bash
cd ~/drone/bench
sudo -v                                  # 0·2번은 드론 정지가 필요하다
SECS=60 WARMUP=10 ./run_bench.sh         # 4개 전체 (약 6분)
SECS=60 WARMUP=10 ./run_fc.sh            # 1·3번만, sudo 불필요 (약 2.5분)
```

해상도를 바꿔 보려면:

```bash
python3 cam_capture.py --fps 15 --width 640 --height 480 --seconds 90 &
python3 cpuwatch.py --seconds 60 --warmup 10 --label "카메라 640x480" --out results/cam_vga.json
```
