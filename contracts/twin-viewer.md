# 트윈 뷰어 계약 — 웹 대시보드와 Unity 뷰어가 같이 보는 문서

**목적**: 가시화 뷰어가 둘이 되었다(브라우저 · Unity 네이티브). 두 뷰어가 같은 계약을
**같게 해석**하지 않으면 같은 대상이 두 화면에서 다르게 보이고, 그때 무엇이 옳은지
판단할 근거가 없다. 이 문서는 그 근거를 한곳에 둔다.

**적용 범위**: `VZ-U-02` · `VZ-I-01` · `VZ-I-02` · `VZ-I-03` · `VZ-U-01` · `VZ-C-03` · `VZ-C-04` · `VZ-C-06`

**와이어 계약의 원본은 이 문서가 아니다.** 원본은 `web-dashboard/mock-gateway/protocol.ts`
이고, 여기 적힌 것은 **뷰어가 그 계약을 어떻게 소비하기로 했는가**다. 둘이 어긋나면
`protocol.ts` 가 이긴다.

---

## 1. 구독 — 무엇을 받는가

구독은 **계약 축** `{entity, node, channel}` 으로만 표현한다. 토픽 문자열을 조립하지 않는다
(`VZ-I-01` / `REQ-704`). 전송 규격이 바뀌어도 상위 코드가 깨지지 않게 하는 것이 이 축의 존재 이유다.

| 채널 | 셀렉터 | 무엇에 쓰는가 | 웹 | Unity |
|---|---|---|---|---|
| `state` | `{*, *, state}` | 상태 3층 (`VZ-U-01`) | ○ | ○ |
| `telemetry` | `{*, *, telemetry}` | 좌표·배터리 (`VZ-U-02`) | ○ | ○ |
| `actuator_state` | `{*, *, actuator_state}` | 액추에이터 도메인 어휘 | ○ | ○ (표시만) |
| `heartbeat` | — | — | ○ | ✕ (씬이 쓰지 않는다) |
| `video_meta` · `video_frame` · `detections` | — | 영상 (`VZ-I-06`) | ○ | ✕ |
| `command_result` · `control_lock` | — | 제어 (`VZ-O-*`) | ○ | ✕ **의도적 제외** |
| `plan` · `plan_progress` | — | 임무 (`VZ-U-07`) | ○ | ✕ |
| `metrics` | — | 지표 (`VZ-I-04`) | ○ | ✕ |

> **Unity 뷰어에는 명령 발행 경로가 없다.** 제어는 웹 대시보드가 한다. 두 곳에서 명령을
> 내면 감사 사슬이 갈리고, 어느 화면에서 누른 것인지가 기록에 남지 않는다.

구독 즉시 서버가 현재값을 1회 푸시한다(`VZ-I-02` / `BE-T-06`). 뷰어는 이 스냅샷을
**걸러내지 않는다.** 없으면 평시 센서는 최대 1분간 빈 자리다.

구독 범위 `scope`(`VZ-I-11`)는 현 단계 `'all'` 고정이며, 두 뷰어 모두 요청에 실어 보내고
봉투에 실려 돌아온 값을 그대로 읽는다(왕복 유지).

레지스트리는 HTTP `GET /registry` 로 최초 1회 조회한다(`VZ-I-03`). 주기 폴링하지 않는다.

## 2. 두 뷰어가 **같은 규칙을 두 번 구현**한 목록

같은 규칙이 TypeScript 와 C# 에 각각 있다. 코드를 옮겨 붙이지 않은 것은 의도다 —
프로세스 경계를 넘는 계약이라 한쪽 타입을 가져다 쓰면 "서버를 갈아끼우면 클라이언트가
깨진다"는 결합이 생긴다. 대신 **어긋나면 어디가 먼저 티가 나는지**를 같이 적는다.

| 규칙 | 웹 | Unity | 어긋나면 어디서 드러나나 |
|---|---|---|---|
| 상태 3층 → 표시 4종 매핑 | `src/data/statusModel.ts` | `Data/StatusModel.cs` | **즉시.** 같은 대상이 한쪽은 정상, 다른 쪽은 판단 불가 |
| `stale` 을 다시 계산하지 않음 | 〃 | 〃 | 사용자 PC 시계가 틀어졌을 때만. **평소에는 안 드러난다** |
| 집약 표기 정규화 (`raw`/객체형 두 철자) | `src/data/aggregation.ts` | `Data/AggregationSpec.cs` | 표기 형식이 바뀌는 날. 한쪽만 `unknown` 으로 떨어진다 |
| 재집약 차단 | 〃 | 〃 (관문만, 뷰어는 집약 안 함) | 뷰어가 요약을 그리기 시작할 때 |
| 권한 범위 판정 (`zones` 에 `*` 포함 여부) | `src/data/permissions.ts` | `Data/TwinStore.ApplyScope` | 좁은 역할로 로그인할 때. `role-narrow` 시나리오 |
| 렌더 병합 100ms | `src/data/mergeScheduler.ts` | `Data/MergeScheduler.cs` | 계측값으로만. 화면으로는 안 보인다 |
| 지수 백오프 (500ms · ×2 · 15s · ±25%) | `src/transport/backoff.ts` | `Transport/Backoff.cs` | 서버 재기동 시 한쪽만 늦게 붙는다 |
| 구독 자동 복원 | `src/transport/WsTransport.ts` | `Transport/GatewayWebSocketTransport.cs` | 재연결 후 한쪽 화면만 빈다 |
| 원천 종류 표기 해석 (`VZ-C-06`) | **아직 없음** | `Data/OriginKindSpec.cs` | 웹에 붙이는 날. 지금은 Unity 만 읽는다 |

> 가장 위험한 줄은 **`stale` 재계산 금지**다. 어겨도 평소에는 두 화면이 같아 보이고,
> 시연 당일 노트북 시계가 몇 분 틀어져 있으면 그때 처음 갈린다. 그래서 두 구현 모두
> 서버가 준 `availability` 를 그대로 쓰고, "최근 수신 N초 전"도 `envelope.ts - last_seen`
> 으로 구한다 — **두 값이 모두 서버 시각이라 클라이언트 시계가 개입하지 않는다.**

## 3. 손잡이(handedness) — 어디서 뒤집기로 했는가

### 결정

**Unity 경계 한 곳(`View/FrameConvert.cs`)에서만 처리한다.** 이 파일 밖에는 축을 만지는
코드가 없다. 백엔드는 손잡이를 모르고, 웹 대시보드도 손대지 않는다.

### 근거 (회의에서 그대로 쓸 것)

계약 `BE-C-04` 는 **축만** 정한다 — `y=위 · 바닥 x-z · 미터`. 손잡이는 말하지 않는다.
그런데 Unity 는 왼손 좌표계이므로, 값이 로보틱스 관례(오른손)로 오면 **좌우가 뒤집혀
보인다.** 회전이 섞이면 눈으로 잡기도 어렵다.

이때 뒤집기를 어디서 할지 두 안이 있다.

1. **백엔드가 뷰어에 맞춰 준다** — 기각. 백엔드가 특정 렌더러의 관례를 떠안기 시작하면
   **뷰어가 둘이 될 때 무너진다.** 웹과 Unity 의 관례가 다른데 한쪽에 맞춰 주면 다른 쪽은
   되돌려야 하고, 그 되돌림은 반드시 여기저기 흩어진다. 뷰어가 셋이 되면 계약이 셋이 된다.
2. **표현하는 쪽이 흡수한다** — 채택. 계약은 하나로 남고, 렌더러 관례는 렌더러가 안다.

이것은 **좌표 변환 금지(`BE-C-04` · `DT-03`)의 예외가 아니다.** 층이 다르다.

| | 하는 일 | 누가 |
|---|---|---|
| **좌표 변환** (금지) | 어느 기준점에서 잰 값인가를 바꾼다. 로컬 → 구역 → 사이트 전역 | **백엔드 단독** |
| **표현 변환** (여기) | 같은 점을 특정 렌더러의 관례로 그린다 | 뷰어 경계 한 곳 |

`VZ-I-01` 을 「브라우저」에서 「가시화 뷰어」로 일반화한 것과 같은 논리다 —
**특정 클라이언트의 사정을 계약에 넣지 않는다.**

### 현재 설정

- Unity 인스펙터 `TwinViewer.flipHandedness` — **기본 OFF**.
- OFF = 수신 좌표를 Unity 왼손계 값으로 그대로 그린다. ON = z 부호를 뒤집는다.
- 기본값 근거는 `unity-twin/README.md` §손잡이 참조.
- 씬에 **비대칭 마커(대문자 F)** 가 있다. 플래그를 뒤집으면 F 가 거울상이 된다.

### 미결

**손잡이 규약이 계약에 없다.** 백엔드가 어느 관례로 값을 내는지 한 줄 확정이 필요하다.
확정되면 플래그를 없애고 한쪽으로 고정한다.

## 4. 원천 종류 표기 (`VZ-C-06`) — **제안이지 계약이 아니다**

목 게이트웨이는 아직 이 표기를 싣지 않는다. Unity 뷰어는 **표기 부재를 `unknown` 으로
다루는 경로**를 구현해 두었고, 그것이 실제로 동작하는지까지가 이번 범위다.

### 실패 방향

> **표기가 없거나 못 읽으면 `unknown` 으로 두고 그 사실을 화면에 표시한다.
> 실물로 단정하지 않는다.**

집약 표기(`VZ-C-03`)에서 한 번 밟은 함정을 반복하지 않기 위한 것이다. "모르면 원본"
으로 떨어뜨렸더니 재집약 차단이 조용히 풀렸다(`src/data/aggregation.ts` 머리말 참조).
여기서 같은 실수를 하면 **표기 없는 시뮬레이션 값이 실물로 기록된다** — 감사에서
훈련과 실제가 같은 모양으로 남는 바로 그 사고다.

집약 표기와 **한 군데가 갈린다**: 집약은 "필드가 없는 채널"이 정상이라 부재를 `raw` 로
본다(상태·명령 채널에는 집약 개념이 없다). 원천 종류는 **모든 값에 붙는 메타**이므로
부재가 정상이 아니다. 그래서 부재도 `unknown` 이고, 사유만 나눈다.

| 사유 | 뜻 | 대응 |
|---|---|---|
| `NotLabelled` | 표기 자체가 봉투에 없다 | 발행 주체가 아직 안 붙였다. **현재 상태** |
| `Unreadable` | 표기는 있는데 계약이 정의하지 않은 값 | **계약 불일치.** 형식을 맞춰야 한다 |

### 필드 형태 제안 (회의 안건)

봉투 최상위에 `origin_kind` 를 둔다. `aggregation` 과 같은 자리, 같은 성격이다.

```jsonc
// 축약형 — 부수 정보가 없을 때
"origin_kind": "real"

// 객체형 — 시뮬레이터가 둘 이상이거나 훈련 세션을 묶어야 할 때
"origin_kind": {
  "kind": "simulated",          // real | simulated | replay  (이 셋만)
  "producer": "unity-sim-01",   // 어느 원천이 만들었나. 시뮬레이터 식별
  "session_id": "drill-2026-0821-01"  // 훈련 세션. 감사에서 같은 훈련을 묶는 근거
}
```

- 축약형/객체형 둘 다 받는 것은 `aggregation` 이 이미 그렇게 되어 있어 형태를 맞춘 것이다.
- **`kind` 는 세 값만 인정한다.** 모르는 철자를 추측해 늘리면 같은 함정을 하나 더 만든다.
- 명령 요청에도 같은 필드를 실어 보낸다(`VZ-C-06` 후단). **이번 범위 밖** —
  Unity 뷰어에 명령 경로가 없고, 웹 대시보드의 명령에 붙이는 것은 별건이다.

### 확정 전까지 지켜야 하는 것

이름이 바뀌면 **Unity 는 `Data/OriginKindSpec.cs` 의 상수 하나**만 고친다
(`OriginKinds.EnvelopeField`). 웹은 아직 구현이 없으므로 그때 같은 규칙으로 만든다.

## 6. 보간 규칙 (`VZ-U-02`)

- 수신값(임무 중 50ms) 사이를 메워 매 프레임 렌더한다. **씬 상태 반영(100ms 병합)과 다른 축이다.**
- 재생은 "지금 - 재생지연" 시각을 그린다. 재생지연은 **관측된 수신 간격**에서 뽑는다 —
  로봇 50ms 와 센서 1분을 하나의 상수로 덮으면 둘 중 하나가 깨진다.
- **최신 표본을 넘어서면 거기서 멈춘다.** 외삽하지 않는다.
- 정지 조건 둘 —
  1. `availability` 가 `stale`·`offline` → **즉시 정지.** 서버 판정이 우선이다.
  2. 마지막 수신 이후 `stale_threshold_ms` 경과 → 정지. **임계는 서버가 준 값을 쓴다.**
     뷰어가 임의 상수를 새로 만들면 두 뷰어의 판정이 갈린다.
- 정지해도 **사라지지 않는다.** 있던 자리에 선다.

## 7. 미결 (이 문서가 답을 기다리는 것)

1. **손잡이 규약** — 백엔드가 어느 관례로 값을 내는가. 현재 뷰어 기본값은 "변환 없음".
2. **`VZ-C-06` 표기의 발행 주체와 필드 형식** — §4 의 제안은 안이다. 붙여 줄 파트가 없으면
   요구사항이 성립하지 않는다.
3. **자세(orientation)가 계약에 없다** — 봉투는 위치만 준다. 로봇이 어느 쪽을 보고 있는지
   그릴 수 없다. `velocity` 로 추정하는 것은 **추정이므로 하지 않았다.**
4. **뷰어 간 불일치의 처리** — 두 화면이 다르게 보일 때 무엇을 믿는지가 정의되어 있지 않다
   (2026-08-21 17:30 보고서 미결 3번).
5. **연결 방식** — Unity 가 게이트웨이에 직결할지 웹 대시보드를 경유할지 미정.
   현재는 직결 구현체 하나이고, 전송이 인터페이스 뒤에 격리되어 있다.
