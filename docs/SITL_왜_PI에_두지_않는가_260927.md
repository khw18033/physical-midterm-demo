# SITL 을 라즈베리파이에 설치하면 무엇이 문제인가

**작성** 2026-09-27 · **질문**: SITL(PX4 + Gazebo)을 `pi3` 안에 설치한다고 하면 문제가 무엇인가
**답 한 줄**: **설치가 되지 않고, 된다 해도 검증 도구가 검증 대상을 오염시킨다.**

관련: [`00_통합개발계획서_x500.md`](00_통합개발계획서_x500.md) 0절(실행 환경이 둘로 나뉘는 이유)

---

## 0. 확인한 사실

`drone/baseline/system-info.txt` 와 `drone/bench/results/03_both.json` 실측값이다.

| 항목 | 값 |
|---|---|
| 기종 | Raspberry Pi 5 Model B Rev 1.1, **aarch64** |
| OS | **Debian GNU/Linux 13 (trixie) 13.7** ← Ubuntu 가 아니다 |
| 코어 | **4** |
| 현재 부하 | 드론 + 카메라 동시에 **14.75%** (`busy_core_pct`) |
| 온도 | 57.6 → 59.3°C (그 부하에서) |
| 스로틀 | `0x0` |

## 1. ★ 설치가 안 된다 — 가장 먼저 막히는 곳

### 1-1. `ubuntu.sh` 는 Debian 에서 **조용히 잘못된 길로 간다**

스크립트는 OS 를 이렇게 판정한다 (`Tools/setup/ubuntu.sh` 54행):

```bash
UBUNTU_RELEASE="`lsb_release -rs`"
```

Pi 는 Debian 13 이므로 이 값이 `13` 이다. 그런데 스크립트의 분기는
`14.04` / `16.04` / `18.04` / `20.04` / `22.04` 만 알고, Gazebo 선택은 이렇게 갈린다 (222행):

```bash
if [[ "${UBUNTU_RELEASE}" == "22.04" ]]; then
    gazebo_packages="gz-garden"          # ← 우리가 원하는 것
else
    ...
    gazebo_packages="gazebo11 libgazebo11-dev"   # ← Gazebo Classic (다른 것)
fi
```

**Debian 13 은 `else` 로 떨어진다.** 결과가 두 겹으로 나쁘다.

| | 문제 |
|---|---|
| ① | **깔끔하게 거부하지 않는다.** 절반쯤 실행되다가 엉뚱한 것을 깐다 |
| ② | 원하는 **Gazebo Garden 이 아니라 Gazebe Classic 11** 을 설치하려 한다 — `gz_x500` 타깃이 쓰는 것이 아니다 |
| ③ | 저장소 경로를 `lsb_release -cs` 로 만드는데 Debian 은 **`trixie`** 를 준다. OSRF 저장소는 Ubuntu 코드네임(`jammy` 등)만 있으므로 **존재하지 않는 경로**가 `sources.list.d` 에 남고 `apt update` 가 깨진다 |

③ 이 특히 고약하다 — **`apt` 가 그 뒤로 계속 경고를 뱉는다.** 드론 컴패니언의 패키지 관리가
망가진 상태로 남는 것이고, 되돌리려면 `sources.list.d` 를 손으로 정리해야 한다.

### 1-2. Debian 에는 Gazebo Garden 공식 바이너리가 없다

OSRF 는 Ubuntu 용 apt 패키지를 배포한다. Debian 13 용 공식 저장소는 없다.
→ **소스 빌드**가 유일한 길이고, Gazebo Garden 소스 빌드는 의존 라이브러리가 수십 개다.
Pi 5 4코어로는 수 시간이 걸리며, 그 과정이 아래 3~6절의 문제를 전부 유발한다.

### 1-3. Gazebo 렌더러

Gazebo Garden 의 기본 렌더러(Ogre2)는 OpenGL 3.3+ 를 요구한다.
Pi 5 의 V3D/Mesa 지원으로 이게 되는지는 **검증되지 않은 경로**다.
물리만 필요하니 헤드리스 서버로 우회할 여지는 있지만, **"될지 모르는 길"에 시간을 쓰는 것**이 된다.

## 2. ★★ 포트 충돌 — 설치가 된다고 가정하면 가장 위험한 문제

### 문제

`config/mavlink-router.conf` 에 이렇게 잡혀 있다.

```ini
[UdpEndpoint local_ctrl]
Mode = Normal
Address = 127.0.0.1
Port = 14540        # ← 제어 스크립트(MAVSDK) 자리
```

그리고 **PX4 SITL 은 기본으로 MAVLink 를 UDP 14540(MAVSDK·offboard)과 14550(QGC)으로 낸다.**
**정확히 같은 포트다.**

### 왜 위험한가

`takeoff_land.py` 의 기본 주소는 `udpin://0.0.0.0:14540` 이다.
`0.0.0.0` 에 바인드해 **오는 것을 받는** 구조라, 같은 Pi 에서 라우터(실물 FC)와 SITL(시뮬 기체)이
동시에 14540 으로 말하면 **스크립트가 어느 기체와 대화하는지 알 수 없다.**

최악의 전개는 이것이다.

> SITL 로 시험한다고 생각하고 `takeoff_land.py` 를 실행 →
> 명령이 **실물 FC 로 간다** → **프로펠러가 달린 기체가 arm 되고 이륙한다.**

포트를 분리하면 피할 수 있다. 하지만 **피해야 할 사고를 스스로 만들어 놓고
설정으로 관리하는 구조**가 된다. 이 저장소의 방침은 그 반대다 —
`DevicePolicy=closed` 처럼 **애초에 불가능하게** 만든다.

> 라우터가 포트를 14540/14541/14542/14543 으로 쪼갠 이유가 바로 "서로 다투지 않게" 였다.
> 거기에 시뮬레이터를 같은 번호로 끼워 넣는 것은 그 설계를 정면으로 거스른다.

## 3. CPU·워치독 — **빌드만 해도 비행 스택이 흔들린다**

| | |
|---|---|
| 현재 부하 | 4코어 중 **14.75%** (드론 + 카메라) |
| 빌드 중 부하 | 4코어 **100%** |

문제는 단순한 느려짐이 아니다. **`drone-detect.service` 에 `WatchdogSec=60` 이 걸려 있다.**

```
빌드가 4코어를 점유
   → fc_detect 가 60초 안에 WATCHDOG=1 을 못 보냄
   → systemd 가 프로세스를 죽임
   → Restart=always 로 재시작 → drone.target 내려갔다 올라옴
   → 라우터 재시작 → FC 링크 끊김
```

즉 **SITL 을 쓰기도 전에, 빌드하는 행위 자체가 P1-5(3단계 재확인)의 기준을 무너뜨린다.**
"침범하지 않았다"를 증명해야 하는 상황에서 침범 요인을 새로 들여오는 셈이다.

온도도 15% 부하에서 이미 59°C 다. 4코어 풀로드는 스로틀 영역으로 들어간다.

---

## 4. SD 카드

PX4 소스만 **2.6G**, 빌드 산출물이 추가로 수 GB, Gazebo 모델·패키지가 또 수 GB.

이 저장소는 이미 SD 카드를 경계한다 — [체크리스트 §4-1](../drone/FLIGHT_CHECKLIST_x500.md) 이
*"비행 중 전원이 끊기면 SD 카드 파일시스템이 깨질 수 있다"* 며 첫 비행 동안
`drone-agent` 정지를 권한다. 스풀 쓰기 정도를 걱정하는 환경에
**수 GB 쓰기를 반복하는 빌드**를 올리는 것은 방향이 반대다.

---

## 5. 전원

Pi 가 드론 BEC 에서 급전받는다. 비행 전 점검 항목이 `vcgencmd get_throttled` = `0x0` 인데,
**4코어 풀로드는 최대 전력 draw** 다. 벤치 전원으로 하면 완화되지만 —
**벤치에 올려놓고 할 일이라면, 노트북에서 하지 않을 이유가 없다.**

---

## 6. ★★★ 가장 근본적인 문제 — 목적이 무너진다

SITL 의 가치는 하나다.

> **실기에 닿기 전에, 안전한 곳에서 확인한다.**

그 "안전한 곳"을 **실기 컴퓨터**로 만들면 격리가 사라진다.
검증 도구가 검증 대상과 같은 CPU·같은 SD 카드·같은 포트를 쓰게 되고,
문제가 생겼을 때 **시뮬 탓인지 실기 탓인지 가릴 수 없다.**

이건 계획서 P1 의 교훈과 같은 구조다 — `dronelink.py` 하나를 건드리는 것이
서비스 셋을 위협하기에 기준선을 먼저 떴다. **SITL 을 Pi 에 넣는 것은 그 원칙을 정반대로 적용하는 것이다.**

그리고 실용적으로: **노트북에 이미 준비돼 있다.**
PX4 v1.15.4 소스 2.6G, Python 의존성, ninja 전부. Gazebo 하나만 남았다.
Pi 에서 처음부터 다시 할 이유가 없다.

## 7. 그럼 Pi 는 무엇을 하나 — 역할 분담

| | 어디 | 무엇을 |
|---|---|---|
| **개발·시뮬 검증** | Windows 노트북 + WSL2 Ubuntu 22.04 | 코드 작성, 구문·import 검사, `fake_fc`, **SITL** |
| **실물 검증** | **Pi 5 (`pi3`) + FC** | 기준선 수집, 서비스 재시작, arm 시험, 실기 비행 |

계획서 0절이 이미 이렇게 나눠 놓았다. **SITL 은 왼쪽 칸의 일이다.**

## 8. ★ 더 나은 대안 — Pi 의 실제 서비스를 시뮬 기체로 시험하기

"Pi 에서 도는 코드를 시뮬 기체로 시험하고 싶다" 는 요구는 **정당하다.**
`fake_fc.py` 는 인형이라 PX4 의 판단을 재현하지 못하고, 노트북의 SITL 은
Pi 의 실제 서비스(`drone-detect`·`linkmon`·`drone-node`)를 거치지 않는다.

**그건 SITL 을 Pi 에 설치해서 풀 문제가 아니다. 네트워크로 붙이면 된다.**

```
[노트북]  PX4 SITL (gz_x500)
              │ MAVLink UDP
              │ (Tailscale — 이미 깔려 있다)
              ▼
[pi3]     mavlink-router  →  14540 / 14541 / 14542 / 14543
              │
              └─ drone-detect · drone-linkmon · drone-node · 제어 스크립트
                 (실물과 똑같은 서비스 스택)
```

라우터 설정에 **시뮬용 UDP 엔드포인트를 임시로 추가**하면 Pi 의 서비스 스택 전체를
시뮬 기체로 돌려볼 수 있다. Pi 에는 아무것도 설치하지 않는다.

> ⚠ **이때도 2절의 위험은 남는다.** 반드시 **FC 를 분리**하거나
> 정비 모드(`touch ~/drone/state/maintenance`)로 감지기를 재운 뒤에 한다.
> 실물 FC 와 시뮬 기체가 동시에 라우터에 붙는 상태를 만들지 않는다.
>
> `fake_fc.py` 가 *"실물 FC 가 붙어 있으면(`mode=drone`) 스스로 실행을 거부"* 하는 것과
> 같은 안전장치를 이 경로에도 두는 것이 맞다.

**이건 P4 이후에 필요해지면 검토할 일이다. 지금 순서(P0 → P1 → P2)에는 들어 있지 않다.**
