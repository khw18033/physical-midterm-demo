# 착륙 판정 누락 조사와 착륙 감시 로그 추가 (2026-11-11)

대상: `drone/scripts/test_sar.py`, `drone/scripts/test_sar_rtk.py` (flight_runner 가 띄우는 비행 스크립트)

## 요약

- 2026-11-09 시험비행에서 착륙 단계까지 간 10번 모두 `[확인] 착륙 완료 ✔` 가 찍히지 않았다. 10번 모두 LAND 항목(#12) 뒤 미션 진행 번호가 항목 수(13)로 넘어갔고, 스크립트는 지상에서 사용자 중단(8번) 또는 시간 초과(2번)로 끝나며 RTL 을 보냈다.
- 가설: LAND 를 마치는 순간 PX4 가 진행 번호를 13 으로 넘겨, 판정 조건 `kind == "land" and tm.in_air is False` 의 두 항이 같은 순간에 성립한 적이 없다.
- 기존 로그는 이 가설과 **어긋나지 않지만 증명하지도 못한다**. 착륙 구간의 `in_air` · `landed_state` · `armed` 를 기록하지 않기 때문이다.
- 그래서 **로그만** 추가했다. LAND 항목이 시작된 뒤에만 `[착륙감시]` 줄을 찍는다. 판정·미션·arm·모드·abort·시간 제한·종료 코드는 그대로다. 다음 비행 로그로 가설을 판정한다(4절).

## 1. 판정 조건 (변경 없음)

`monitor()` 가 0.05초마다 돈다. 착륙 완료는 다음 한 줄로만 판정한다.

```python
if kind == "land" and tm.in_air is False:      # test_sar.py:735, test_sar_rtk.py:797
    log("[확인] 착륙 완료 ✔")
    break
```

- `kind` 는 `mission_raw.mission_progress().current` 로 `plan.roles` 를 찾은 값이다. 범위 밖(예: current=13)이면 `"?"` 가 된다.
- `tm.in_air` 는 `telemetry.in_air()` 스트림의 최신값이다.
- 판정이 안 되면 시간 제한(`예상 비행시간 × 2 + 60초`)에 걸려 `TimeoutError` → `--abort`(기본 rtl) → exit 1.

### 2.2 진행 번호가 13 이 된 시점과 in_air 가 False 가 된 시점의 선후

**로그로 알 수 있는 것**
- 10번 모두 진행 번호가 13(= 항목 수)에 도달했다.
- 진행 번호가 12 인 동안(6~21초) 판정은 한 번도 성립하지 않았다. 판정 루프는 0.05초마다 돌므로, 「진행 번호 12 이면서 최신 in_air 가 False」인 상태가 확인 시점에 걸린 적이 없다. 즉 그런 상태가 있었더라도 50ms 를 넘지 않았다.
- 진행 번호가 13 이 된 뒤 몇 분 동안 ModeLost 가 나지 않았다(허용 모드는 `{MISSION}` 하나). MAVSDK 가 알려 준 모드는 계속 MISSION 이었다(모드 스트림이 살아 있었다는 전제에서).
- 131535: 진행 번호 13 이후 고도 약 0m 인 채로 1.5~1.9 m/s 로 39m 이동했고 헤딩도 크게 바뀌었다(out 154~175줄). 사람이 들고 옮긴 것으로 보인다.

**로그로 알 수 없는 것**
- in_air 가 False 로 바뀐 시점. 어디에도 기록되지 않는다. 진행 번호보다 먼저인지, 동시인지, 나중인지, 끝내 바뀌지 않았는지(None 이거나 수신 태스크가 죽은 경우 포함) 가를 수 없다.
- 진행 번호가 바뀐 정확한 시각(해상도 2초).
- landed_state 값(LANDING / ON_GROUND).

**추정 (이 장비에서 소스를 확인하지 않음)**
- MAVSDK 의 `in_air` 는 EXTENDED_SYS_STATE 의 landed_state 에서 만들어지며 LANDING 도 공중으로 친다.
- PX4 가 LAND 항목을 끝내는 것과 ON_GROUND 를 보고하는 것은 같은 land detector 판정에서 나온다. 두 시점이 거의 겹칠 수 있다는 뜻이고, 가설과 같은 방향이지만 증명은 아니다.

### 2.3 `Telem._pump` 가 값을 받는 방식

- 폴링이 아니라 gRPC 스트림을 `async for` 로 받는다. 값이 올 때마다 속성을 덮어쓰고 **최신값 하나만** 남긴다. 이력과 수신 시각은 남지 않는다.
- 주기: position · velocity 만 `set_rate_*` 로 10Hz 를 요청한다. in_air · flight_mode · mission_progress · heading · gps 는 FC 기본 주기다. in_air 는 EXTENDED_SYS_STATE 주기를 따른다(`drone/README.md` 표에는 5Hz, 실측 아님).
- 판정 루프는 이 최신값을 0.05초마다 읽는다.
- 수신 태스크가 예외로 죽으면 아무 출력 없이 값이 마지막 값에 멈춘다.

### 2.4 착지 후 자동 disarm(COM_DISARM_LAND) 근거 — 없다

- 스크립트는 arm 전에 `armed()` 를 한 번 읽을 뿐, 그 뒤로는 받지 않는다.
- mav.csv 에는 ATTITUDE · GLOBAL_POSITION_INT · GPS_RAW_INT · LOCAL_POSITION_NED · SYSTEM_TIME 만 있다. HEARTBEAT · EXTENDED_SYS_STATE 가 없다.
- 간접 정황은 131535 에서 사람이 기체를 옮긴 것뿐이다. 확인하려면 FC 의 .ulg 를 봐야 한다.

### 2.5 지상에서 보낸 RTL 의 결과

- **FC 가 명령을 받아들였다.** 10번 모두 `[중단] rtl 명령을 보낸다` 바로 다음이 `[종료]` 이고, `[오류] rtl 실패` · `[복구]` 줄이 없다. `mavsdk_guard.abort()` 의 `_send` 가 5초 안에 예외 없이 돌아왔다는 뜻이다. MAVSDK 는 ACK 가 실패면 예외를 던진다.
- **다시 뜬 흔적은 없다.** mav.csv 의 relative_alt 를 RTL 시각부터 다음 실행 시작까지 보면 10번 모두 −1.5 ~ +1.5 m 안이다(착지 후 표류 범위).
- **모드가 실제로 RTL 로 바뀌었는지, arm 이 됐는지는 근거가 없다.**

### 3.2 동작

- **언제 시작하나:** 이번 미션에서 진행 번호가 LAND 보다 작은 값을 한 번 받은 뒤, LAND 이상인 진행 번호를 처음 받는 순간. 이전 미션의 묵은 값으로 잘못 시작하지 않도록 「작은 값을 먼저 봤다」를 조건으로 둔다. 판정 루프(0.05초)와 상관없이 **값이 도착하는 순서대로** 기록한다.
- **언제까지:** `tm.stop()` 까지. 그래서 사용자 중단·시간 초과 뒤 RTL 을 보낸 다음에 도착한 모드·armed 변화도 남는다. 단 스크립트는 ACK 를 받자마자 끝나므로 그 뒤에 도착한 값은 놓칠 수 있다(대기 시간을 넣으면 종료 시점이 바뀌므로 넣지 않았다).
- **찍는 줄:**

| 줄 | 언제 | 내용 |
|---|---|---|
| `[착륙감시] 시작` | 감시 시작 때 한 번 | cur · in_air · landed · armed · mode · alt · vz, 속성별 마지막 수신 경과 시간, 끝난 수신 태스크 수 |
| `[착륙감시] 변화` | prog(current/total) · in_air · landed · armed · mode 중 하나라도 바뀔 때 | 바뀐 항목(이전→이후)과 현재 값 전체, 감시 시작부터의 시각 t |
| `[착륙감시] 상태` | 2초마다 (10Hz 로 오는 position 수신에 맞춰) | 위 값 + alt(`relative_altitude_m`) · vz(`velocity_ned.down_m_s`, +가 하강) |
| `[착륙감시] 요약` | `fly()` 의 finally 에서 한 번 | 아래 참고 |
| `[착륙감시] 내부 오류` / `준비 실패` / `… 수신 끊김` / `요약 실패` | 감시 코드에 예외가 날 때 | 한 줄 남기고 감시를 끈다 |

- **요약 줄 모양:**
  ```
  [착륙감시] 요약 판정창(cur=12∧in_air=False) 겹침=0.000s/0회 | cur 12→13 t=+2.536 | in_air→False t=+2.556(cur 이탈 기준 +0.020s) | landed→ON_GROUND t=+2.567(cur 이탈 기준 +0.030s) | armed→False t=+3.067(cur 이탈 기준 +0.531s) | 감시 3.1s | 끝 cur=13/13 in_air=False landed=ON_GROUND armed=False mode=RETURN_TO_LAUNCH
  ```
  - `겹침` = 진행 번호가 LAND 이면서 in_air=False 인 상태가 이어진 시간 합계와 횟수. 「#12 LAND 진행 중 in_air=False 를 본 적이 있는가」에 대한 답이다.
  - `cur 이탈 기준` = 각 사건이 진행 번호가 LAND 를 떠난 순간보다 몇 초 늦었는지(음수면 먼저).
  - 값을 한 번도 받지 못했으면 `None`, 사건이 없으면 `없음` 으로 찍는다.
  - LAND 전에 끝난 비행은 요약을 찍지 않는다.
- **가시화 웹 정규식과 겹치지 않게:** 새 줄은 모두 `[착륙감시]` 로 시작하고, `#`, `진행`, `착륙 완료`, `PASS`, `[중단]`, `[오류]`, `[종료]`, `고도`, `속도` 를 쓰지 않는다. 기존 줄은 하나도 바꾸지 않았다.

### 3.3 새 구독 2개: `telemetry.landed_state()`, `telemetry.armed()`

- **왜 필요한가:** armed 없이는 자동 disarm(2.4)과 RTL 뒤 arm 여부(2.5)를 알 수 없다. landed_state 가 있어야 LANDING / ON_GROUND 를 가르고 in_air 와 비교할 수 있다.
- **영향:** Python 쪽은 gRPC Subscribe 요청만 보낸다(`mavsdk/telemetry.py` 3333 · 3354줄, MAVSDK 3.17.4). 값은 이미 들어오고 있는 HEARTBEAT(1Hz)와 EXTENDED_SYS_STATE 에서 나온다. `set_rate_*` 를 부르지 않으므로 새 MAVLink 명령은 없다. mavsdk_server 쪽에서 구독할 때 아무것도 보내지 않는지는 소스로 확인하지 못했다. 부하는 localhost 에서 초당 약 6건이다.
- **범위:** LAND 감시가 시작될 때 만들고 `tm._tasks` 에 넣는다. LAND 전에는 존재하지 않고, 끝날 때 `tm.stop()` 이 함께 정리한다.

### 3.4 제어 흐름에 영향이 없다는 근거

- `monitor()`, 판정 조건, 미션 구성 · 업로드 · `clear_mission`, arm, 모드 전환, abort, 시간 제한, 종료 코드는 한 줄도 바꾸지 않았다(diff 는 추가만 있다).
- 새 코드는 Telem 의 기존 속성을 읽기만 한다. 쓰는 것은 새 이름(`landed`, `armed`, `lw`, `_lw_*`)뿐이다.
- `_lw_feed` · `lw_prepare` · `lw_summary` 는 `except Exception` 으로 감싸고, 로그 쓰기 자체도 `_lw_log` 에서 예외를 삼킨다. 그래서 감시 코드가 깨져도 기존 수신 태스크(`_pump`)와 판정 루프는 계속 돈다.
- `CancelledError` 는 BaseException 이라 잡히지 않는다. Ctrl+C · SIGTERM 은 지금처럼 전달된다.
- 새 코드에는 await 가 없다(추가 구독 태스크 제외). 동기 로그 몇 줄뿐이라 이벤트 루프를 붙잡지 않는다.
- LAND 전에는 `lw_prepare` 가 값만 저장하므로 출력이 지금과 같다. 예외: plan 에 LAND 항목이 없으면 `[착륙감시] 준비 실패` 한 줄이 LAND 전에 찍힌다. `build_plan()` 이 항상 LAND 를 마지막에 넣으므로 실제로는 일어나지 않는다.

- 두 파일의 diff(추가 줄)가 완전히 같다.

  - LAND 전에 끝난 비행은 요약을 찍지 않는다.
- 기존 `drone/flight_runner/test_flight_runner.py` 31개 통과.
- **실기체 · SITL 로는 돌려 보지 않았다.** `fake_fc.py` 는 미션을 지원하지 않는다. 첫 실비행 전에 `--dry-run` 이 지금처럼 끝나는지(LAND 전에 끝나므로 `[착륙감시]` 줄이 없어야 함)는 확인하는 것이 좋다.

| `겹침=0` 이고 in_air→False 가 cur 이탈보다 늦거나 ±0.05초 안 | **가설이 맞다.** 지금 조건으로는 착륙 판정이 구조적으로 성립할 수 없다 → 5절 |
| in_air→False 가 cur 이탈보다 0.1초 넘게 먼저이고 `겹침>0` 인데 `[확인] 착륙 완료` 가 없음 | **가설이 틀렸다.** 판정 루프 쪽(블로킹 등)을 조사해야 한다 |
| in_air 가 끝까지 True 또는 None, landed=ON_GROUND | 원인이 다르다. in_air 매핑이나 수신 쪽 문제. `시작` 줄의 `마지막수신 in_air=…` · `끝난수신태스크` 를 함께 본다 |
| armed→False 가 cur 이탈 뒤 약 COM_DISARM_LAND 초에 나옴 | 착지 후 자동 disarm 확인 |
| `[중단] rtl …` 뒤 mode · armed 변화 줄 | 지상 RTL 의 실제 결과. 아무 줄도 없으면 .ulg 로 확인 |

- 시각은 Python 이 값을 받은 시각이고 스트림마다 따로 받으므로, 수십 ms 차이에는 의미를 두지 않는다.
