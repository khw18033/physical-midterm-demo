# pi3 — X500 v2 드론에 올라가는 라즈베리파이

드론 기체에 실려 나는 **라즈베리파이 5 한 대**의 전부다.
이 한 대가 성격이 전혀 다른 **두 가지 일**을 동시에 한다.

```
                         ┌──────────────────────────────────────┐
                         │      라즈베리파이 5  (pi3)            │
                         │                                      │
   [FC / PX4] ──UART──▶  │  ① drone/       비행 컨트롤러 연동    │  ──▶ QGroundControl
                         │                                      │      가시화 웹
                         │                                      │
   [카메라]   ──MJPEG──▶ │  ② drone_rpi/   영상 말단 에이전트    │  ◀── 엣지 서버가
                         │                                      │      당겨 간다
                         └──────────────────────────────────────┘
```

| 폴더 | 하는 일 | 상대 |
|---|---|---|
| [`drone/`](drone/) | 비행 컨트롤러(PX4)와 대화. 상태를 읽고 명령을 시작시킨다 | FC, 지상국, 가시화 웹 |
| [`drone_rpi/`](drone_rpi/) | 카메라 프레임을 잡아 정렬해 두고 엣지에 내준다 | 카메라, 엣지 서버 |

### ⚠ 이 둘은 서로 모른다

코드상 참조가 **한 방향도 없다.** 같은 파이에 살면서 **CPU만 나눠 쓴다.**
한쪽이 죽어도 다른 쪽은 멀쩡하고, 고칠 때도 따로 고친다.

유일한 접점은 자원이다. 실측(2026-09-22, Pi 5 4코어):

| 돌리는 것 | 시스템 부하 | 온도 |
|---|---|---|
| ① 비행 연동만 | 5.1% | 60.4°C |
| ② 영상 말단만 | 9.1% | 62.0°C |
| **둘 다 (실제 운용)** | **13.8%** | **64.2°C**, 스로틀 없음 |

거의 정확히 더해지고 서로 손해 보는 구간이 없다. 자세한 측정은
[`drone/REPORT_cpu_agent_260922.md`](drone/REPORT_cpu_agent_260922.md).

# ① `drone/` — 비행 컨트롤러 연동

> 자세한 내용은 **[`drone/README.md`](drone/README.md)** 에 따로 있다. 여기서는 요약만 한다.

## 무슨 일을 하나

비행 컨트롤러(코아 FC H743, PX4)와 시리얼로 대화해서

- 기체 상태를 읽고 (자세·위치·배터리·GPS·비행모드)
- 지상국 QGroundControl 이 붙을 창구를 열어 주고
- 가시화 웹에 상태를 중계하고
- 필요할 때 이륙·착륙 명령을 **시작**시킨다

**비행 자체는 하지 않는다.** 비행은 FC 가 한다.

## 구조 한눈에

```
[FC TELEM2] ──UART 921600──▶ /dev/ttyAMA0 ──▶ mavlink-router ──┬─ TCP  5760 → QGroundControl
                                                               ├─ UDP 14540 → 제어 스크립트 (MAVSDK)
                                                               ├─ UDP 14541 → 링크 감시
                                                               ├─ UDP 14542 → 자동 감지
                                                               └─ UDP 14543 → MQTT 가시화 브리지
```

시리얼 포트는 한 번에 하나만 열 수 있는데 FC 와 대화하고 싶은 쪽은 여럿이다.
`mavlink-router` 가 시리얼을 독점하고 **패킷을 복사해 여러 창구로 뿌린다.**

## 전원만 켜면 된다

`drone-detect` 가 10초마다 FC 를 찾는다. 찾으면 `drone.target` 을 켜고,
링크가 15초 끊기면 내린다. 현재 상태는 `drone/state/mode` 에 `drone`/`none` 으로 적힌다.
FC 전원이 파이보다 늦게 들어와도 알아서 붙는다.

| 유닛 | 언제 | 하는 일 |
|---|---|---|
| `drone-detect` | 항상 | FC 탐색·링크 감시 |
| `drone-mavlink-router` | FC 있을 때 | 시리얼 ↔ 창구 중계 |
| `drone-linkmon` | FC 있을 때 | 링크 통계 (읽기 전용) |
| `drone-node` | 항상 | MQTT 가시화 브리지 (읽기 전용) |

## 지상국

QGroundControl → **TCP `100.85.243.54:5760`** (Tailscale 경유).
현장 망이 핫스팟으로 자주 바뀌어서 Tailscale IP 를 쓴다 — 어느 망에 있든 그대로다.

## 안전 원칙

- **기본은 읽기 전용.** 기체를 움직이는 스크립트는 2개뿐이고 자동 실행에는 하나도 없다
- **FC 파라미터는 읽기만 한다.** 변경은 사람이 QGC 로만
- **OFFBOARD 모드를 쓰지 않는다.** 이륙·착륙은 "한 번 말하면 FC 가 알아서" 하는 방식이라
  **비행 중 파이가 죽어도 기체가 떨어지지 않는다**
- 약속이 아니라 구조로 막는다 — 읽기 전용 유닛은 `DevicePolicy=closed` 로 시리얼을 **열 수조차 없다**

**비행시킬 때는 [`drone/FLIGHT_CHECKLIST_x500.md`](drone/FLIGHT_CHECKLIST_x500.md) 를 연다.**

# ② `drone_rpi/` — 영상 말단 에이전트

## 핵심 개념 먼저: 말단은 "보지" 않는다

이름이 에이전트라 뭔가 똑똑한 걸 할 것 같지만, **일부러 아주 단순하게** 만들었다.

| 말단(이 파이)이 한다 | 말단이 **하지 않는다** |
|---|---|
| 카메라에서 최신 프레임 잡기 | 검출 (무엇이 있는가) |
| 프레임 간 **움직임** 추정 (KLT) | 추적 (같은 물체인가) |
| 엣지가 요청하면 프레임 내주기 | 의미 해석 |
| 엣지 판정을 **현재 좌표로 옮겨** 내보내기 | 거리 산출 |

검출·추적·거리는 전부 **엣지 서버** 몫이다. 파이에는 신경망이 아예 없다
(`requirements.txt` 에 `onnxruntime` 조차 없다 — `numpy` 와 `opencv` 둘뿐이다).

### 왜 이렇게 가벼운가 — 58배 이야기

예전에는 말단이 RPN 신경망으로 후보 200개를 만들고 ByteTracker 로 ID 를 붙였다.

```
RPN 896x512 + ByteTrack   ~350 ms/frame     ← 예전
KLT 플로우 200점 @640x360    6.0 ms/frame   ← 지금  (58배 싸다)
```

합성 검증(실제 이동 37, -14 px)에서 둘 다 `(37.0, -14.0)` 을 정확히 냈다.
**정렬에 필요한 것은 "움직임"이지 "정체성"이 아니었기 때문이다.**
게다가 RPN 이 만들던 후보를 실제로 쓰는 쪽이 없었다.

> 그 흔적으로 `drone_rpi/models/mobilenet_rpn_p1_896x512.onnx` (20MB) 가 남아 있는데
> **어느 코드도 참조하지 않는 고아 파일**이다. 정리 대상이다.

## 풀려는 진짜 문제 — "판정이 도착하면 이미 낡았다"

```
  t=0.0s   말단이 프레임 N 을 엣지에 줌
  t=0.9s   엣지가 "여기 사람 있음, 박스 (x,y,w,h)" 회신
           ↑ 그 사이 기체가 움직여서 화면은 이미 프레임 N+7 이다.
             박스를 그대로 그리면 엉뚱한 자리에 붙는다.
```

얼마나 어긋나나 — focal_px 590, 속도 5m/s, 왕복 0.9초 기준:

| 대상 거리 | 화면상 어긋남 |
|---|---|
| 20m | **133 px** |
| 50m | 53 px |
| 100m | 27 px |
| (yaw 10°/s 회전만으로도) | 122 px |

**해법**: 말단이 매 프레임 "직전 대비 얼마나 움직였나"를 KLT 로 쌓아 둔다.
판정이 오면 그 프레임부터 지금까지의 누적 변환으로 **박스를 현재 좌표로 옮긴다.**

### 낡음을 숨기지 않는다

옮긴 결과에는 항상 `age_s`(얼마나 오래됐나), `quality`(누적 드리프트),
`frames_late`, `observed_at`, `applied_at` 이 붙는다.
두 물체가 스칠 때 박스가 뒤바뀔 수 있는데, `quality` 가 그걸 **드러낸다**.
판정은 6초(`obstacle_ttl_s`)가 지나면 만료된다 — 만료가 없으면 수십 초 전 판정이 화면에 남는다.

## 통신 구조 — 엣지가 **당겨 간다** (pull)

**말단은 엣지 주소를 모른다.** 먼저 연결하지 않으므로 알 필요가 없다.

```
[엣지 서버]  ──GET /api/frame?since=N&wait=5──▶  [말단 pi3:8890]
             ◀──── 프레임 + 메타 (multipart) ────
             ──POST /api/verdict (판정 결과)───▶
```

이렇게 한 이유:

- **backpressure 가 공짜로 생긴다.** 엣지가 당기는 속도가 곧 처리 속도다
- **NAT·LTE 에서 안 깨진다.** 요청 IP 를 되찾아 되쏘지 않고 같은 연결의 응답에 실어 보낸다
- **엣지 기기를 옮겨도 말단 설정을 안 고친다**

### HTTP API (포트 8890)

| 메서드 | 경로 | 하는 일 |
|---|---|---|
| GET | `/api/frame?cam=0&since=N&wait=5` | 최신 프레임. `since` 보다 새 게 없으면 **204** (롱폴링) |
| GET | `/api/spool` | 끊겼던 구간에 쌓인 것을 오래된 순서로 |
| GET | `/api/health` | 온도·스풀 상태·통계 |
| POST | `/api/verdict` | 엣지가 끝낸 판정을 밀어 넣는다 |
| POST | `/api/spool/ack` | 받았으니 지워도 된다 |

> `since` 로 중복의 90% 가 사라진다. `204`(새 것 없음)와 `404`(그런 카메라 없음)를
> **일부러 구분**한다 — 같게 다루면 카메라 번호 오타를 영영 못 찾는다.

## 링크가 끊기면 — 디스크 스풀

엣지가 5초 넘게 아예 오지 않으면(= 단절) 그때만 프레임을 디스크에 쌓는다.

> pull 구조에서는 **안 가져간 프레임이 대부분이고 그건 정상이다**(backpressure).
> 그것까지 다 쌓으면 디스크만 태운다. 그래서 "단절일 때만, 1초 간격으로" 두 조건을 건다.

상한은 500개 / 30분이고, 넘치면 **오래된 것의 픽셀부터 버리고 메타는 살린다.**
링크가 돌아오면 엣지가 `/api/spool` 로 훑어 가고 `ack` 에서 지운다
(전송 도중 끊겨도 다시 받을 수 있게 **받은 시점이 아니라 ack 에서** 지운다).

## 카메라

| 항목 | 값 |
|---|---|
| 모듈 | imx708 표준 (Camera Module 3) |
| 해상도 · 프레임률 | 1280×720 @ **8fps** |
| 수평 화각 | 59.0° |
| `focal_px` | 1131 |
| 대수 | **1대** |

`rpicam-vid` 로 MJPEG 파이프를 받아 **항상 최신 프레임만** 처리한다
(`rpicam-still` 은 프레임당 542ms 라 못 쓴다).

> ⚠ **렌즈를 바꾸면 `hfov_deg` 와 `focal_px` 를 반드시 같이 고친다.**
> 말단은 이 값을 쓰지 않고 실어 보내기만 하지만, **엣지의 거리 추정이 이 값을 쓴다.**
> 안 고치면 거리가 약 1.9배 어긋난 채 **조용히** 틀린다.

## 자동 실행

`drone-agent.service` 가 부팅 시 뜬다. 카메라가 빠지거나 `rpicam-vid` 가 죽으면
5초 뒤 재시작한다 — 사람이 없을 때 비행 내내 눈이 감긴 채로 가면 안 되기 때문이다.

> 네트워크를 **요구하지 않는다.** 엣지가 못 붙을 뿐, 캡처와 정렬은 돌아야 한다.

배포는 `deploy.sh` (venv 방식이 비행 정본). `Dockerfile` 은 카메라 없는 기기에서
코드가 도는지 보는 **재현·CI 용**이다 — `rpicam-vid` 가 호스트 libcamera 에 묶여 있어서
컨테이너로 카메라를 돌리면 버전이 어긋날 때 **조용히** 실패한다.

# 공통

## 지금 상태 (2026-09-23)

| 항목 | 상태 |
|---|---|
| ① 비행 연동 | 0~3단계 통과. **이륙(4·5단계)은 아직 안 해봤다** |
| ② 영상 말단 | 캡처·정렬 동작 중. **엣지가 아직 한 번도 안 붙었다** (`served: 0`) |

② 의 스풀이 상한(500)에 차 있는 것은 고장이 아니다 — 엣지가 없으니 설계대로 쌓고 버리는 중이다.

## 빠른 확인

```bash
# ① 비행 연동
cat ~/drone/state/mode                      # drone = FC 연결됨 / none = 없음
systemctl status drone-detect
cd ~/drone && ./venv/bin/python scripts/fc_state.py     # FC 상태 (읽기 전용)

# ② 영상 말단
systemctl status drone-agent
curl -s localhost:8890/api/health | python3 -m json.tool

# 공통
vcgencmd measure_temp && vcgencmd get_throttled         # 0x0 이어야 정상
```

## 파이썬 환경이 둘이다

목적과 의존성이 완전히 달라서 **섞지 않는다.** 시스템 python 에는 아무것도 깔지 않는다.

| 환경 | 주요 패키지 |
|---|---|
| `drone/venv` | `pymavlink`, `mavsdk`, `paho-mqtt` |
| `drone_rpi/venv` | `numpy`, `opencv-python-headless` (신경망 없음) |

> ⚠ **`pip install -U mavsdk` 금지.** 4.x 는 API 가 다른 별개 패키지라 제어 스크립트가 전부 깨진다.
> 복구: `drone/venv/bin/pip install -r drone/config/requirements.lock.txt`

## 저장소에 대하여

이 저장소의 루트는 **홈 디렉터리**다. 홈에는 세션 기록·에디터 서버·다른 리모트를 가진
`hw/` 가 섞여 있어서 `.gitignore` 를 **화이트리스트**로 짰다 — `/*` 로 전부 무시하고
`drone/`, `drone_rpi/`, 문서만 되살린다. 블랙리스트로 짰다가 하나 빠뜨리면 곧장 유출이다.

추적하지 않는 것: `venv/`(합 545MB), `logs/`, `state/`, `spool/`,
`drone/src/`(mavlink-router 업스트림 50MB), `/etc` 를 가리키는 심볼릭 링크.
